Add transactional mode. A route with `mode: "transactional"` (validated with `ROUTE_MODE_INVALID`; `MODE_UNSUPPORTED` when the store has no `openTransaction()`) runs its handler inside one database transaction, exposed as `ctx.tx`, and writes the idempotency record in that same transaction, so the record and the handler's writes commit or roll back together (contract section 7). A returned response is stored with the record and sent only after `COMMIT` succeeds, and replays like any other; a returned 5xx is stored too. A throw rolls everything back and is answered with a 500 `about:blank` problem that is not stored, so a retry runs the handler again (row 13). A release status rolls everything back and is returned as-is (row 11). When the record cannot be written (including when the handler caught a failed statement and left the transaction aborted), or `COMMIT` is rejected or its outcome is unknown, the request is answered 503 store-unavailable with `Retry-After` and the handler's response is never sent. A concurrent request with the same key waits on the uncommitted record for up to the store's `lockTimeout` (default `"250ms"`, validated with `LOCK_TIMEOUT_INVALID`), then gets a 409 in-flight with `Retry-After` set to that timeout in whole seconds (minimum 1); under `REPEATABLE READ` or `SERIALIZABLE`, a serialization failure while claiming the record is answered the same way. The lock timeout covers only the statements that claim the record; the previous `lock_timeout` is restored before the handler runs. The transaction is the lease, so `ctx.renew` is absent in that mode (`HandlerContext` is now `LeaseHandlerContext | TransactionalHandlerContext`), and in lease mode `ctx.tx` is absent. Handlers must not run `BEGIN`, `COMMIT` or `ROLLBACK` on `ctx.tx` (savepoints are fine), and `ctx.tx` is dead once the transaction ends: a later query rejects with `IdemfenceStoreError` code `TRANSACTION_ENDED` without reaching the connection. A request without a key on an optional-key transactional route runs in a plain transaction with no record, and so does a request whose method the fetch adapter does not enforce (for example a GET on a POST and PATCH route): adapters hand such requests to the new `Idemfence.passthrough(request, route, handler)`. `failOpen: true` cannot be combined with `mode: "transactional"` (`IdemfenceConfigError` code `FAIL_OPEN_TRANSACTIONAL`). idemfence never takes a second connection while a transaction is open.

For stores: `SqlExecutor` (`query(text, params)` returning `{ rows, rowCount }`) is the interface a `pg` `Pool` or `PoolClient` already satisfies, and every operation of `idemfence/postgres` accepts one as an optional last argument to run inside a caller's transaction. `TransactionalStore.openTransaction()` returns a `StoreTransaction` (`executor`, `commit()`, `rollback()`); its failures are `IdemfenceStoreError`s with the driver's error as `cause`: `TRANSACTION_UNAVAILABLE` (nothing ran), `COMMIT_REJECTED` (rolled back for certain, including a transaction a failed statement had already aborted) and `COMMIT_UNKNOWN` (the connection failed during `COMMIT`); a client whose connection broke or whose `ROLLBACK` failed is destroyed instead of returned to the pool. The caller's `pg.Pool` must have a `pool.on("error", ...)` handler, as the README shows.

Add the transactional-mode plumbing. `SqlExecutor` (`query(text, params)` returning `{ rows, rowCount }`) is the interface a `pg` `Pool` or `PoolClient` already satisfies; every operation of `idemfence/postgres` accepts one as an optional last argument so the record can be written inside a caller's transaction, and `postgresStore` takes a `lockTimeout` option (default `"250ms"`, validated with `LOCK_TIMEOUT_INVALID`). `withTransaction(pool, { lockTimeout? }, fn)` runs `fn` on one pooled client inside `BEGIN` and `SET LOCAL lock_timeout`, commits when it resolves, rolls back when it rejects (rethrowing the rejection unchanged), and destroys the client instead of returning it to the pool when the connection broke or `ROLLBACK` failed. Its own failures are `IdemfenceStoreError`s with the driver's error as `cause`: `TRANSACTION_UNAVAILABLE` (nothing ran), `COMMIT_REJECTED` (the server answered `COMMIT` with an error, rolled back for certain) and `COMMIT_UNKNOWN` (the connection failed during `COMMIT`, outcome unknown). A route with `mode: "transactional"` (validated with `ROUTE_MODE_INVALID`; `MODE_UNSUPPORTED` when the store has no `transaction()`) runs its handler inside such a transaction and exposes it as `ctx.tx`, with `ctx.renew()` running on that transaction rather than on a second pool connection; in lease mode `ctx.tx` is absent. A transaction that cannot be opened or whose `COMMIT` is rejected is answered 503 store-unavailable with `Retry-After` and the key freed; a connection failure during `COMMIT` is answered 503 with the lease kept, since the handler's writes may have landed. The record itself still follows lease mode until the transactional contract rows land. The caller's `pg.Pool` must have a `pool.on("error", ...)` handler, as the README now shows.

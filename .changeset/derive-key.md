Add derived downstream keys. Every handler context (lease, transactional, and the fail-open run of row 14) has `ctx.deriveKey(label)`, which resolves to 64 lowercase hex characters: an HMAC-SHA256, keyed with the oldest configured secret, of the length-prefixed tag `idemfence/derive/v1`, the request's lookup key and the label (contract section 5, test vectors in Appendix A). Every attempt of the same request derives the same key, so a handler can pass it as the idempotency key of a downstream call such as a payment and the downstream side effect happens once across retries, lease takeovers and fail-open runs. A label must be 1 to 128 printable ASCII characters (0x21 to 0x7E), otherwise the call rejects with the new `IdemfenceDeriveError` code `DERIVE_LABEL_INVALID`; on a request without an `Idempotency-Key` it rejects with code `DERIVE_KEY_UNAVAILABLE`. `previousSecrets` is documented as newest first, oldest last: rotating a new secret in (the old one moves to the front of `previousSecrets`) changes no derived key, and removing the oldest secret is a deliberate re-key that changes every derived key. Derived keys never appear in logs. New exports: `IdemfenceDeriveError`, `IdemfenceDeriveErrorCode` and `DeriveKey`.
